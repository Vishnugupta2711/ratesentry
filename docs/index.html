Engineering
How it works
Four layers working together to make distributed rate limiting atomic, consistent, and fast.
Client → AWS ALB → FastAPI node 1 → ElastiCache Redis → Lua script (atomic) → 200 or 429
01 — Algorithm
Sliding window counter
Maintains a time-ordered log of request timestamps per user in Redis sorted sets. Expired timestamps outside the 60-second window are pruned on every check — the window slides with the clock, eliminating the burst loophole at fixed window boundaries.
ZREMRANGEBYSCORE key 0 (now - 60s)
count = ZCARD key
if count < limit: ZADD key now now
02 — Atomicity
Lua script in Redis
The check-and-increment is a single Lua script executed server-side in Redis. No other command can interrupt between the read (ZCARD) and write (ZADD). This makes race conditions structurally impossible — not just unlikely — regardless of how many concurrent requests arrive.
-- Runs atomically inside Redis
local count = redis.call('ZCARD', key)
if count < max then
  redis.call('ZADD', key, now, now)
  return 1 -- allowed
end
return 0 -- blocked
03 — Distribution
Shared state across nodes
All FastAPI nodes connect to the same ElastiCache Redis cluster. A user's counter lives in Redis — not in any node's memory. Node 1 and Node 2 always agree on how many requests a user has made, even if every alternate request hits a different node.
Node 1 → Redis: user_A count = 8
Node 2 → Redis: user_A count = 9
Node 1 → Redis: user_A count = 10
Node 2 → Redis: BLOCKED (limit=10)
04 — Resilience
Fail-open design
If Redis becomes unreachable, RateSentry fails open — requests are allowed through rather than returning 500 errors. A CloudWatch alarm fires within 30 seconds. ElastiCache replica auto-promotes if the primary fails. The API never goes down because Redis went down.
try:
  return redis.lua_check(key)
except RedisError:
  cloudwatch.alarm("redis-down")
  return True # fail-open

Engineering depth
The decisions behind the design
Every architectural choice was made for a specific reason — not cargo-culted from a tutorial.
Why Lua scripts instead of Redis transactions?
Redis MULTI/EXEC transactions don't support conditional logic — you can't check a value and conditionally write based on it inside a transaction. Lua scripts run server-side with full scripting capability and are atomic by design. ZCARD and ZADD must execute as one operation — two separate calls create a TOCTOU race condition where two simultaneous requests both see count=99, both proceed, and the counter reaches 101. Lua makes this structurally impossible.
Why sliding window instead of token bucket?
Token bucket allows a burst at window boundaries — a user sends 100 requests at 11:59:59 and 100 more at 12:00:00, hitting 200 requests in 2 seconds while technically never violating the per-minute rule at any single moment. Sliding window measures any rolling 60-second span continuously, eliminating this loophole entirely. The tradeoff is memory — sorted sets store one entry per request vs one number for token bucket — but at 100 req/user/min that's a trivial overhead.
What happens if Redis goes down?
Fail-open policy: if Redis is unreachable, requests are allowed through rather than returning 500 errors. A CloudWatch alarm fires within 30 seconds. ElastiCache replica auto-promotes to primary in ~60 seconds if the primary fails. The reasoning: a brief window of unlimited requests is acceptable downtime. Taking the entire API offline because the rate limiter is down is not — especially when the rate limiter sits in the critical path of every request.
How does it scale beyond 2 nodes?
FastAPI nodes are completely stateless — no user data, no counters, no session. Adding capacity is attaching more EC2 instances to the ALB target group. Redis is the only stateful component: scale it vertically (larger ElastiCache instance) or via Redis Cluster sharding by user ID hash. At Google scale you'd add geographic distribution — a user in Mumbai hits a Redis node in Mumbai, not Virginia — but the application code doesn't change, only infrastructure configuration.
